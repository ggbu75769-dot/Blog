# 32. 기획을 ‘독자에게 남는 답’까지 연결하는 명세

## 1. 원고를 쓰기 전 필요한 것
인기 키워드, 부제, 분량만 입력하지 않는다. 독자 상황, 지금 필요한 질문, 핵심 답, 그 답을 뒷받침할 재료가 있어야 한다.

| 항목 | 좋은 입력 | 부족한 입력 |
|---|---|---|
| 독자 상황 | 앱에 사진은 보여서 백업이 끝났다고 생각하지만 기기 용량을 비워야 함 | 사진에 관심 있는 사람 |
| 중심 질문 | 지금 지우려는 사진의 기기 사본과 백업본을 어떻게 구별할까 | 구글 포토 장점 |
| 글의 새 가치 | 보여지는 목록·백업 상태·정리 후 접근 방식의 차이를 한 판단 순서로 묶음 | 다른 글을 쉽게 요약 |
| 구체적 재료 | 공식 도움말의 서로 다른 두 기능과 적용 조건 | 사용자 경험을 상상해 생성 |
| 제목 약속 | 백업 여부를 판단하는 기준 제공 | 절대 잃어버리지 않는 완벽한 방법 |

## 2. 사실 장부와 편집 재료를 나눔
사실 장부는 ‘이 말을 해도 되는가’를 관리한다. 편집 재료는 ‘왜 이 글을 읽어야 하는가’를 관리한다. 원출처마다 `verified_fact`, `scope`, `reader_consequence`, `usable_detail`, `missing_proof`를 기록한다. 근거가 있는 사실을 무작정 모두 넣지 말고 중심 질문에 필요한 것을 선택한다.

구체적 재료는 다음 중 해당하는 것으로 확보한다. 개수 할당량은 아니다.
- 조건을 맞춘 실제 비교.
- 숫자의 뜻을 이해시키는 명시적인 가상 계산.
- 문서 A와 문서 B를 연결해 생기는 판단 기준.
- 실제 확인한 장면과 가능한 해석의 차이.
- 작성자가 제공한 사용·방문·측정 자료.
- 불확실한 부분과 적용되지 않는 예외.

허위 후기·상상한 인터뷰·확인하지 않은 대사·근거 없는 ‘요즘 다들’은 구체적인 재료가 아니다.

## 3. 본문에 실제로 있는 보상 연결
각 주요 편집 기여는 다음 구조로 기록한다. 이름만 ‘독창성’이라고 채우지 않는다.

```
reader_before: 독자가 글을 읽기 전 혼동하거나 모르는 것
reader_after: 읽은 뒤 구별·판단·이해·감상할 수 있는 것
payoff_kind: 비교 / 설명 예 / 해석 / 판단 기준 / 관찰
exact_anchors: 최종 본문 block_id와 실제 문구
source_ids: 해당 사실이 연결된 근거
comparison_scope: 어떤 자료와 범위 안에서 새 가치라고 평가했는가
```

이 데이터는 작성자의 자기 칭찬이 아니다. 별도 편집 검토 서비스가 최종 본문에서 확인해 만든다. `reader_after`가 있어도 정확한 본문 위치가 없으면 반환한다. 위치가 맞아도 그 내용이 가치 있다는 의미적 판단은 별도다.

## 4. ‘어떤 주제에도 붙는 글’ 검사
서비스명·상품명·인물명을 다른 대상으로 바꿔도 대부분 그대로 통하는 문단을 찾아낸다. 이는 경고 휴리스틱이지 자동 차단 공식은 아니다. 배경 설명·안전 안내·연결 문장은 범용적이어도 필요한 역할을 할 수 있다.

최종 편집자는 그 문단에서만 얻는 것이 무엇인지 확인한다. 답이 없으면 삭제·합치기·실제 근거 보충 중 하나를 고른다. 무작위 숫자나 개인 일화를 넣어 구체적으로 보이게 만들지 않는다.

## 5. 문단을 지웠을 때 달라지는 것
문단별로 새로운 사실, 설명, 비교, 판단, 예외, 장면 맥락, 전환, 감정적 의미 중 역할을 확인한다. 삭제해도 정보·이해·흐름·감상이 달라지지 않는 문단은 우선 수정 후보다.

모든 문단에 새로운 사실이 하나씩 있어야 하는 것은 아니다. ‘문단당 사실 수’나 ‘구체명사 비율’을 품질 점수로 쓰지 않는다. 반복이 필요한 핵심 안전조건은 유지한다. 연결 문장을 무조건 지워 끊기는 글을 만들지 않는다.

## 6. 수요와 완성 원고의 독립 검사
좋은 설명 샘플을 보고 지금 인기 있는 주제라고 표시하지 않는다. 실제 기획에서는 게시 가능 시점, 관심 신호의 출처·관측일·시간 해상도와 채널 적합성이 필요하다. 자료가 없는 주제는 ‘수요 미검증’으로 두되 개발용 문체 예제로 사용할 수 있다.

## 7. 두 블로그 배정
기획의 핵심 질문과 답을 비교하여 같은 원고를 여러 블로그에 말투만 바꿔 복제하지 않는다. 두 글의 독자·핵심 답·근거 차이가 실제로 설명될 때만 별도 기획한다. 원고와 개인 경험의 범위는 R1 scope 계약을 유지한다.
