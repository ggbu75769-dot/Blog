# 09. 품질보증·블라인드 평가 명세

문서 기준: 2026-09-15 · 설계 동결: 4.1.0-r1 · 공개 게시: 사용자 수행


## 세 층의 검사
L1 결정적 검사: 스키마, 범위, 버전, 만료, 파일, 권리, 예산, 중복, 공개/비공개 누출, 단위·날짜 형식.
L2 의미 검사: 주장 추출, 원문 지지 여부, 사실→해석 구분, 제목 약속, 경험 서술, 비교 조건, 블로그 문체, 새로운 기여.
L3 실제 사용자 검사: 원고 자연스러움, 답의 충족, 수정시간, 실제 네이버/티스토리 에디터 수동 전송, 모바일 가독성.
L1 성공을 L2·L3 성공으로 표시하지 않는다.

## 게이트
| 게이트 | 실패 예 | 처리 |
|---|---|---|
| G-SOURCE | 최신 주장의 원문 미확인·상충·읽기 범위 과장 | 조사 보강 또는 보류 |
| G-CLAIM | 편집 중 조건·숫자·대상이 변함, orphan claim | 해당 블록 수정 후 재검수 |
| G-ORIGINAL | 같은 질문/답 재작성, 의미 없는 표 | 기획 재설계 |
| G-EXPERIENCE | 가짜 사용기·작성자 사실 누출 | 즉시 차단, 공개자료형 대안 |
| G-ASSET | 이미지 없음·권리 없음·실제효과처럼 보이는 생성물 | 대체/재기획/보류 |
| G-PROMISE | 제목의 숫자·비교·답이 본문에 없음 | 제목 또는 본문 수정 |
| G-VOICE | 상투적 반복·다른 블로그 말투·과장 | 제한된 문체 수정 |
| G-EXPORT | 파일 누락·내부메모·HTML XSS·내용 누락 | 렌더 수정 후 재검수 |
| G-FRESH | 재검토 기한 초과·원문 변경 | READY 취소, 재조사 |
| G-SCOPE | 다른 tenant/blog 개인 자료 접근 | 작업 중단, 보안 감사 |

GateReport는 revision_id, target_content_hash, evidence_bundle_hash, policy_version, issuer, checked_at, valid_until, findings, verdict를 가지며 review service가 저장한다. writer 응답은 gate_report 권한을 가질 수 없다. 작성 모델이 ‘모두 통과’라는 문구를 넣어도 무시한다. 검수기에는 같은 self-score가 아니라 실제 자료와 최종 원고를 전달한다.

## 최종 본문을 다시 읽는 이유
작성 중 claim_id가 붙은 문장만 보면 연결되지 않은 새로운 사실이 빠질 수 있다. 검수기는 제목·도입·표·캡션·본문 전체에서 사실 후보를 추출하고 research claims와 대응한다. 캡션과 그림이 암시하는 효과도 검사한다. 모델이 발견하지 못할 가능성은 실제 표본 평가와 정정률로 관측한다.

## 출시 평가 셋
계약시험·단위시험용 합성사례는 artifacts에 제공한다. 별도로 개발 후 실제 자료에서30편을 만들고 최소2개 프로필·3개 글형식을 포함한다. 최신 정보·부족한 이미지·상충 출처·경험 부재·표가 있는 원고를 포함한다. 이미 수작업으로 잘 고친 예시만 골라 자동 성능을 측정하지 않는다. 평가셋은 본문·소스 접근 범위·권리를 보존한다.

## 인간 평가 절차
평가자2명이 버전·모델명·기획점수를 보지 않고 글을 읽는다. 자연스러움, 블로그 관점, 새 답의 가치, 제목과 본문 일치, 과장을5점으로 평가하고 수정 시간을 기록한다. 독립 판단 후 불일치를 토론하되 원래 점수는 남긴다. 구체적인 블로그 관점을 모르는 평가자는 해당 항목을 N/A로 표시한다. 자동 AI 판별기 결과로 대체하지 않는다.

## 평가 목표
중대 오류0건; 자연스러움 중앙값4/5 이상·개별 원고3 미만0건; 제목 약속 위반0건; 필수 자산 누락0건. 수정시간 중앙값5분 이내는 제품 개선 목표이며 초기 데이터로 재설정할 수 있다. 모든 기준은 proposed이지 검증된 과거 성능이 아니다. 고위험 주제는 기준 완화가 아니라 별도 사람 검토가 필요하다.

## 테스트 계층
- UNIT: 시간·숫자·범위·hash·합계·성능 계산·권리·상태 함수.
- CONTRACT: JSON schema·API 에러·공급자 응답 정제.
- INTEGRATION: PostgreSQL 트랜잭션·RLS·lease·예산·파일 저장.
- ADVERSARIAL: 외부 prompt injection, tenant 누출, 무한 재시도, HTML, 경로 탈출.
- E2E_REPLAY: 고정된 증거로 두 블로그의 원고 생성 흐름.
- E2E_LIVE: 실제 허용 소스와 유료 모델 연결, 원고 출력까지. 게시 제외.
- MANUAL_EDITOR: 사용자가 실제 에디터에 복사·삽입·미리보기를 확인.
이 문서 작성 시 CONTRACT 자산의 문서 검증만 실행한다. DB/LLM/실제에디터 시험은 개발 이후 수행한다.


## R1: 검사 수준과 출고 경계
필드별 JSON Schema 뒤에 의미상 날짜/구간/분모 검사, cross-file 범위/버전 검사, 실제 파일 검사, 최종 글의 의미 검사, 사람 확인을 순서대로 적용한다. writer의 payload_type은 실제 스키마에 결속한다. produced+null, PASS+critical, human_required+미확인은 거부한다. 본문이 그대로여도 근거·허가범위·프로필이 바뀌면 이전 검수는 무효다. `assess_handoff`는 인증된 서버가 가져온 검수 자료에 대한 결정적 참조이며 임의 JSON issuer 문자열만으로 검수 주체를 인증하지 않는다.


## R2 보완 우선 적용
내용·문체·독자 평가·독자용 출력의 상세는 docs/31~38을 함께 적용한다. 특히 부족한 내용은 문체로 덮지 않고 조사/재기획하며, 최종 본문의 실제 payoff 구절과 review 버전을 연결한다. R1 사실·권리·scope·최신성 gate는 약화하지 않는다. R2 예제는 인간평가·실제 에디터·트렌드 효과가 확인되지 않은 편집 기준용 원고다.
