# 36. R2 개발 작업계획과 작업명세

## 호환성
패키지 릴리스는 4.2.0-r2. R1 ArticleIR 등 기본 데이터 스키마는 4.1.0을 유지한다. R2 편집 검토는 별도 `r2.editorial.1` sidecar로 추가한다. 기존 원고 해시를 몰래 재서명하거나 기존 gate를 새 본문에 승계하지 않는다. 기존 60개 작업과 140개 제품 인수시험은 계속 유효하고 모두 미실행 상태를 유지한다. R2 추가 작업 10개와 예정 제품 인수시험 30개는 `contracts/r2/work.json`에 별도 명시한다. 참조 코드는 제품 구현 완료가 아니다.

## 단계 1 — 실제 한 편을 먼저
독자용 렌더러와 세 예제를 연결하고 원고와 sidecar를 분리한다. 사용자에게 보이는 본문에 내부 주석·보안 시험 문구가 들어가지 않는지 확인한다. 이 단계에 전체 서비스 재설계나 DB 전면 재작성은 필요 없다.

## 단계 2 — 기획·집필 품질 경로
자료에서 실제 기여를 만들고 부족하면 조사로 돌린다. 최종 본문에 payoff 앵커를 연결한다. 문체 편집 후 의미를 다시 검사한다. 실제 공급자 모델은 허용된 연결·예산이 확인된 경우에만 호출한다. 없다면 REPLAY 자료로 API·작업 흐름을 개발한다.

## 단계 3 — 사람 평가와 조건부 확장
블라인드 평가·수정시간 기록을 실제로 수행한다. 작성자의 자기평가를 독자 평가로 저장하지 않는다. 처음부터 모든 주제의 자동 품질 승인을 켜지 않고 검증된 형식·주제 범위만 확장한다.

## 내부 API 추가안
`api/r2/editorial.openapi.yaml`의 경로는 서비스 내부 API 제안이며 네이버 제공 API가 아니다. 블로그/원고/버전 경로의 scope를 서버에서 인증한다. write tool에 reviewer identity를 위임하지 않는다. 평가자는 원고 본문은 읽을 수 있어도 발행 권한·개인 비밀키를 받지 않는다.

## 데이터 저장·이전
별도 editorial_reviews 테이블 또는 기존 검수 저장소의 버전 확장에 원고 FK·revision FK·content_hash·reviewer service·policy version·차원 판정·앵커·실행 분류·created_at을 저장한다. 실제 DB 스키마는 저장소 확인 후 migration으로 반영한다. 임의로 운영 DB를 변경하지 않는다. 새 상태는 R1 작업 상태와 충돌하지 않도록 작업 결과로 매핑하고, 구조 변경이 필요하면 schemas/API/DDL을 함께 동기화한다.

## 검증 명령
```
python tools/verify_checksums.py
python tools/validate_bundle.py
python tools/run_r1_checks.py
python -m unittest discover -s tests/r2 -v
python tools/build_r2_previews.py
```
기존 검사와 새 검사를 독립적인 서비스 기능 수로 합산하지 않는다. R2 모델 집필·독자 평가·실제 에디터·홈피드 효과는 별도 미실행 목록에 남긴다.
