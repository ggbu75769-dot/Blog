# 30. 릴리스 게이트와 반복 개선 종료 기준

## 무한 개선 대신 증거가 있는 단계 상승
사용자의 '완벽해질 때까지'는 확인되지 않은 완료를 선언하지 말고 발견한 결함을 계속 줄이라는 기준으로 적용한다. 실제 운영 없이 성장·문체·에디터 호환성을 확정할 수 없으므로 그 시험은 명시적으로 남긴다. 문서만 추가하거나 합성 테스트 개수만 늘려 완성도를 표시하지 않는다.

| 게이트 | 필요한 결과 | 지금의 상태 |
|---|---|---|
| R0 문서·스키마 | 모든 참조·예제·버전·작업DAG 일치 | 실행 결과 JSON 참조 |
| R1 결정적 규칙 | 정상·반례·cross-language·파일 변조 검사 | 실행 결과 JSON 참조 |
| R2 데이터/권한 | 실제 PostgreSQL·RLS·동시성·예산·재시작 | NOT_RUN |
| R3 실제 자동원고 | 허가 소스·실제 모델·이미지→파일 일관성 | NOT_RUN |
| R4 바로 쓸 품질 | 사람 평가·수정시간·네이버/티스토리 전송 | NOT_RUN |
| R5 사업 성과 | 실제 게시·유입·성숙한 성과·월 목표 기여 | NOT_RUN |

## R0/R1 종료 조건
고친 문제의 반례가 재현 가능하고 수정 후 거부되어야 한다. 정상 입력이 계속 통과해야 한다. 수정으로 생긴 새 실패를 고치고 전체 회귀를 다시 돌린다. 문서·기계 계약·통합본·파일 hash를 최종으로 맞춘다. 테스트 실패를 skip하거나 임계값을 완화해서 통과시키지 않는다. 외부 환경 부재는 NOT_RUN으로 분리한다.

## 제품 릴리스 go/no-go
R0/R1만으로 실운영 출시를 선언하지 않는다. R2~R4가 대상 채널에서 증거를 갖춘 뒤 제한된 운영을 시작한다. R5는 실제 성과를 확인하는 운영 과정이며 월100만 약속으로 대체할 수 없다. 수동 게시 기능은 계속 사용자에게 남긴다.

## 다음 개선 입력
실제 Codex 구현 diff, 회귀/통합 실패 로그, 사람이 고친 원고 전후, 실제 에디터 출력, 원본 통계, 운영 비용을 다음 라운드의 입력으로 삼는다. 이 자료가 생기기 전에는 예측된 개선 효과를 실적처럼 기재하지 않는다.


## R2 보완 우선 적용
내용·문체·독자 평가·독자용 출력의 상세는 docs/31~38을 함께 적용한다. 특히 부족한 내용은 문체로 덮지 않고 조사/재기획하며, 최종 본문의 실제 payoff 구절과 review 버전을 연결한다. R1 사실·권리·scope·최신성 gate는 약화하지 않는다. R2 예제는 인간평가·실제 에디터·트렌드 효과가 확인되지 않은 편집 기준용 원고다.
